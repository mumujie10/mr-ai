## A. GUI 引擎能力对齐

这一组的共同原则：**能力由引擎广播，GUI 只呈现与约束**。缺哪一档就在适配层补哪一档，不在组件里散写引擎名。协议差异全部留在 `src-tauri/src/engine/`（见 [02-架构与数据流](./02-架构与数据流.md)）。

### 1. 推理强度 Effort —— 部分

- **已有**：`src/features/chat/store/preferences.ts` 的 `setEffort`；推理强度滑块按引擎广播档位裁剪（任务 #28）。
- **还缺**：① 每个引擎实际接受的值域与 CLI 自身默认值的对齐表（现在只有"能选哪些"，没有"选了之后 CLI 真的收到什么"）；② 引擎不上报档位时的呈现与落点；③ 切引擎 / 切渠道后档位是否保留或降级的明确规则（关联已修的 #45）。
- **完成标准**：一张"引擎 × 档位 × 传入形式"的对照表进代码注释或本文件，`use-engine-models` / 滑块侧用例覆盖"广播档位缺失""档位被渠道降级"两种；真机至少两引擎各试一次。

### 2. Todo 列表渲染 —— 已实现待核对

- **已有**：`src/features/chat/TasksPanel.tsx` + `components/agent-task-steps.ts` 的 `deriveTodoList` / `stepsFromDelegation`，`RunStatusStrip` 里的 `TodoRows`，以及 `TasksPanel.test.tsx`。
- **还缺**：跨引擎核对。各家 CLI 的 todo 工具形状不同（内置运行时 / claude / codex / omp），当前解析可能只覆盖了其中几种；未完成项与已完成项的排序与"整表替换 vs 增量更新"的语义要在事件层定清楚，否则中途刷新会跳序。
- **完成标准**：为每种 todo 载荷形状各写一条事件流回归；在真实会话里核对面板与 CLI 自己的显示一致。

### 3. 子代理展示（任务分发面板）—— 部分

- **已有**：回合进行中的子代理可见（`SubagentRows`、运行状态条里的子代理计数与滚动行统计）。
- **还缺**（= 任务 #35 的 B 路线）：**接收 → 落库回放 → 请求通道与停止**三件事。现在子代理只剩"回合中可见"，刷新或重开会话就看不到；无法向子代理发指令，也没有独立停止入口。
- **风险**：落库回放涉及转录结构变更，要兼顾旧会话兼容与插件扩展点；先定数据形状再动 UI。

### 5. 斜杠命令与技能选择器 —— 已实现待核对

- **已有**：引擎广播的斜杠命令与技能进入 `/` 选择器（任务 #27）；`slash-command-menu.tsx` 及其测试；宿主自己的应用级命令（打开设置 / 插件中心 / 市场 / 版本记录 / 快捷键）。
- **还缺**：① 三类来源（引擎广播 / 技能目录 / 宿主内置）在同一列表里的分组与优先级是否稳定；② 命令带参数时的补全与提示；③ 引擎重连后命令表刷新的时机。
- **完成标准**：分组顺序、去重与空态有测试钉住；接一台真实引擎核对广播与界面完全一致。

### 6. 渠道 / 供应商切换 —— 部分

- **已有**：输入框的渠道选择（`src/components/application/ai-chat/engine-model-panel.tsx` 的 `ChannelPicker`）、设置里的渠道编辑器与"测试连接"（只测草稿不写存储）、推理档位与渠道的联动缺陷已修（#45）。
- **还缺**：**会话进行中切渠道**的语义——当前会话继续用原渠道，还是新渠道从下一条生效？两种都要能解释，且切换要能看见（现在渠道重存后容易留下"档位落不到被选渠道"这类隐性问题）。
- **完成标准**：把选定语义写进 `docs/ui-ux-spec.zh-CN.md` 并加回归；界面上任何时候都能回答"这条会话现在走哪个渠道、哪个模型、哪一档"。

### 7. Fast 模式（service tier）—— 部分

- **已有**：`AppSettings.ompOpenaiServiceTier`、`codexServiceTier`（`default` / `priority`），OMP 侧的闪电开关与行为已文档化在 [omp-fast-mode.md](./omp-fast-mode.md)；`setOmpServiceTier` / `setCodexServiceTier`。
- **还缺**：① 其他引擎（内置运行时、kimi、grok、pi、dsh 等）是否接受同类档位、以什么参数形式；② Fast 会**增加额度或费用消耗**，这个提示目前只在 OMP 文档里，界面侧是否处处可见；③ 界面标记只表达"请求偏好"，不代表服务端确认——这条要不要在 UI 上更明确地说。
- 入口先查 CLI 帮助/协议再动适配器，**不要为验证发付费请求**（上游 OMP 验证的口径就是这个）。

### 8. `/compact` 压缩上下文 —— 部分

- **已有**：宿主发起（store 的 `compactContext` 发 `/compact`，压缩后刷新用量）、自动压缩阈值与幕布（`ui-ux-spec` §3.1）、宿主调度行不显示为气泡的契约（`tests/browser/auto-compact-curtain.html`）。
- **还缺**：**引擎原生 `/compact` 的直通**与"引擎不支持时怎么办"。现在是宿主代发命令，若某引擎的压缩语义/参数不同（或直接没有该命令），需要明确降级路径与提示文案，不能静默失败。
- 注意内部行判定：`isCompactCommandRow` 只认正好 `/compact`，带尾巴就不算——扩展时要一并核对。

### 9. `/mcp` —— 部分

- **已有**：宿主自己的 MCP 模块（`src/features/mcp/`：设置页 `McpSection`、命令面板 `McpCommandPanel`、探测 `probe-store`、详情弹窗），`/mcp` 作为应用级命令由宿主接管。
- **还缺**：**与引擎原生 `/mcp` 的关系定义**——是宿主面板统一接管，还是把命令透传给 CLI？两者的配置来源可能不一致（引擎自己的 MCP 配置 vs 宿主写入的），要先定权威源，否则会出现"面板里看得见、引擎里没生效"。

## C. 账号、发布与商业能力

### 10. 更新功能替换成我们自己的 —— 待决策

- **现状**：自动更新的 `endpoints` 指向上游仓库；代码签名身份不是本团队的；bundle identifier 也是上游的（任务 #34）。发布链路与版本对齐口径见 [团队规范/分支提交与评审](./团队规范/分支提交与评审.md) 与 [团队规范/安全与隐私红线](./团队规范/安全与隐私红线.md)。
- **要做的事**：换成我们自己的更新通道与签名身份；决定包标识与已有用户的升级路径；顺手决定 `.github/workflows/pr-target-branch.yml` 里仍写死上游账号的那条门禁（现在会让目标 `main` 的 PR 必红）。
- **边界**：这三项**必须由你决定并操作**，AI 与新成员不得自行改（供应链与发布身份）。

### 11 / 14 / 15. 用户登录、算力与充值、会员订阅 —— 待决策（方向变更）

**这三项不是普通功能开发，是产品方向的变更**，先说清冲突：

1. 本产品的既定方向是 **只走 BYOK**（用户自带渠道密钥），不引入云端账号体系；此前已经**主动删除**了 MiniMax 业务埋点与 telemetry 命令面、每日签到云客户端、反馈上传、自动错误诊断上报、云端权限分类器、CLI 侧远端 Skill Hub（任务 #7、#14、#16–#19）。
2. 登录 / 计费 / 会员意味着重新引入**服务端账号 + 外发 + 支付边界**，与 [团队规范/安全与隐私红线](./团队规范/安全与隐私红线.md) 的两条直接冲突：已拔除的外发能力不许复活；任何新增外发都要显式评审（发什么、发到哪、谁触发、能否关闭、失败怎样）。
3. 代码与界面**当前完全没有**账号、算力、订阅、会员的任何实现或文案（设置里的 OAuth 相关是 Pi/OMP 这类外部 CLI 的供应商登录，不是本产品账号）。

**动工前需要先定的**（一次定清，避免做到一半推翻）：

- 账号体系与 BYOK 的关系：**并存**（登录只用于计费/官方内容，模型仍走用户自己的渠道）还是**替代**（登录后由我们代理模型调用）？后者会改变整个产品的密钥模型。
- "算力"是**我们代付的模型额度**，还是**官方内容的计价单位**？兑换与扣费的权威账本在哪、离线怎么办、退款怎么算。
- 会员付费走哪个渠道，**谁承担支付合规与发票/退款责任**；支付信息一律不得进应用日志与本地明文。
- 登录失败、未登录、掉线三种状态下的功能边界：未登录是否仍然能完整使用 BYOK（强烈建议"能"，否则现有用户升级即失效）。
- 手机端（远程访问）是否允许登录态与支付操作。

这四问没答案之前，本条保持 `待决策`，不排实现。

## D. 官方内容中心

### 16. 插件 / 智能体 / Skills / MCP 合并 —— 部分

- **已有**：四类各自独立可用——插件（`src/features/plugins/`：中心、市场、运行时、权限；命令面板有"打开插件中心 / 市场"）、智能体（`src/features/bots`，设置 → 系统 → 智能体）、Skills（`src/features/skills`，CLI 侧远端 Hub 已删）、MCP（见第 9 条）。
- **你要的形态**：一个统一入口，**用户下载官方的东西就能直接用**。
- **还缺**：① 统一目录与"官方"身份标识（现在只有插件市场有官方徽标）；② 一套安装/更新/卸载流程覆盖四类（现在是四套）；③ 官方内容的托管位置与分发渠道（这属于外发与供应链，需与第 10 条一起定）；④ 依赖关系：智能体可能引用技能、技能可能引用 MCP，装一个要能带出依赖；⑤ **离线可用性与失败说明**——不能下载成功但引擎里没生效。
- **风险**：合并 UI 容易，合并"谁是权威源"难。建议先定四类内容的存储与生效路径，再谈界面合并；否则会出现"中心里显示已安装、运行时里找不到"。
