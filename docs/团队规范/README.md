# 团队规范

这个目录是**协作规则**：一个改动怎么走完"提出 → 实现 → 验证 → 合入 → 发版"。
项目本身的事实（模块在哪、数据怎么流、命令怎么跑）在上一级：[../README.md](../README.md)。

## 分类

| 规范 | 管什么 | 什么时候必须翻 |
|---|---|---|
| [代码与命名](./代码与命名.md) | 目录归属、命名、注释纪律、**必须成对同步的镜像清单** | 写代码前；改到 token / i18n / SDK / 设置字段时 |
| [分支提交与评审](./分支提交与评审.md) | `main` 开发 + tag 发版、提交粒度、评审要点、并行改动 | 提交与开 PR 前 |
| [文档与界面文案](./文档与界面文案.md) | 谁改谁更新、变更记录、版本记录、i18n 双语、品牌口径、`cli/` 边界 | 改了任何用户可见的东西 |
| [安全与隐私红线](./安全与隐私红线.md) | 密钥、日志、外发、系统权限、剪贴板、插件权限、供应链 | 碰到凭据 / 网络 / 权限 / 依赖 |

## 优先级

1. **安全与隐私红线**高于一切便利。
2. 与仓库根 [AGENTS.md](../../AGENTS.md) 冲突时，以 AGENTS.md 的项目级禁令为准（例如"严禁主动提交"）。
3. 与本目录其他文档冲突时，**以代码为准**，并在同一个改动里把文档改对——文档说了而代码没做，和代码做了而文档没说，都算缺陷。

## 这些规范怎么长出来

它们不是照着模板抄的通用条款，每条都对应这个仓库里真实踩过的坑：某个 token 改名后样式被静默丢弃、后端命令漏了手机桥那一处、`--wait` 把一次网络抖动变成整次发布失败、缓存副本把另一端刚写的设置冲回去。

**新增规则的门槛**：规则要能落到具体文件、命令或测试上，并且来自真实问题。加规则时优先合并重复项、删掉失效内容，而不是不断往上堆段落。没有对应事实的"最佳实践"不要写进来。

## 谁维护

规范本身也是代码库里的文件：改它同样走 [分支提交与评审](./分支提交与评审.md) 的流程，需要至少一个维护者同意。各模块负责人的名单在 [../01-项目地图.md](../01-项目地图.md) 的所有权表里，目前待填——在填上之前，跨模块改动一律找人评审。
