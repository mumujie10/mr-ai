# 分支提交与评审

## 分支模型

**在 `main` 上开发，按 tag 发版。** 日常改动合入 `main`，发版时打 tag 并手动触发发布流水线（`.github/workflows/release.yml`，仅 `workflow_dispatch`；Windows 走 `build-windows-artifact.yml`）。发版前要改的版本号一共五处：`package.json`、`src-tauri/Cargo.toml`（`Cargo.lock` 跟着走）、`src-tauri/tauri.conf.json`、`src/version/changelog.ts` 的 `CHANGELOG_DATA`、以及 git tag——本地打包命令见 [../03-开发环境与日常命令.md](../03-开发环境与日常命令.md)，签名身份与更新源的归属见 [安全与隐私红线](./安全与隐私红线.md)。

> ⚠️ 现存冲突，需要维护者选定：`.github/workflows/pr-target-branch.yml` 仍按上游的"日常 PR 进 `vX.Y.Z` 开发分支、`main` 只收维护者从 `v*` 分支发起的 release PR"来拦，且白名单里写的是**上游作者的账号**。按现在的模型，这条门禁会拦维护者自己。三种收口方式：改白名单 / 换分支模型 / 删掉这条 workflow。选定前，把它当成"会误报的检查"，不要为了让它闭嘴而临时开 `vX.Y.Z` 分支。

需要临时隔离大改动时开短命分支（`feature/<简短行为>`），合完即删；不要长期存在与 `main`  diverge 的平行分支。

## 提交

- **不擅自提交。** 改动完成后先报告结果，等维护者明确说"提交"再提交；**历史授权不顺延**——上一次同意过，不代表这次同意。
- **推送由维护者执行。** 验证通过的改动可以本地提交，但 `git push` 需要当前对话里的明确指示。
- **一个提交一件事**：功能改动与它的测试、它的文档更新放同一个提交（"谁改谁更新"要求同一个改动内完成）；无关清理单独提交。
- **提交信息写行为变化**：做了什么、为什么、验证到什么程度。不写文件清单，不写任务编号黑话。
- **只暂存本次相关文件**：`git add <路径>`，不用 `git add -A` / `git add .`。提交前 `git status` 看清混进了什么——别人未提交的内容、临时脚本、`.env` 类机密都不该出现。
- **不跳过校验**：不用 `--no-verify`、不放宽断言、不跳过测试、不改验收标准来制造通过。检查挂了先查根因。

## 并行改同一个仓库

本仓允许多人/多会话同时工作：

1. 动手前 `git status --short`，看清哪些文件已有别人的未提交改动。
2. 批量改写（统一文案、统一命名）**跳过脏文件**，把冲突留给对应作者。
3. 共享工作树里**不要用裸 `git stash` / `stash pop`**；需要暂存就用带唯一 tag 的方式，并只删自己创建的那条。
4. 破坏性命令（`reset --hard`、`checkout --`、`clean -f`、`rebase`、`push --force`）先确认有没有人的未提交工作会被吞掉，不确定就先停下来问。

## 评审

**谁能评**：所有权表（[../01-项目地图.md](../01-项目地图.md)）的负责人栏目前待填。填上之前：跨模块改动、任何碰到下面清单的改动，必须至少一个维护者同意才能合入。

**必须评审的改动类型**

- `packages/plugin-sdk`、扩展点、权限目录（对外契约）
- `settings.rs` 字段增删（涉及老用户文件的键迁移与 flatten 往返）
- `src-tauri/src/engine/` 协议适配、进程生命周期
- 数据库与历史扫描（旧会话兼容）
- 新增依赖、构建与签名发布配置
- 系统权限、剪贴板、网络外发（对照 [安全与隐私红线](./安全与隐私红线.md)）

**评审者检查清单**

- [ ] 根因位置对不对：是修在真正负责它的模块，还是在 UI 上层糊了一层？
- [ ] 影响面是否沿调用链查过（生产方、消费方、兼容路径、失败路径）？
- [ ] 后端命令是否三处都注册了（命令 / `invoke_handler` / `web/dispatch.rs`）？
- [ ] 三态设置字段是否区分了"没设置"和"明确关"？
- [ ] 镜像清单是否同步（token↔`cx.ts`、字段↔`ipc.ts`/设置页/搜索/双语、SDK↔skill 文档）？
- [ ] 缺陷用例是否**先红后绿**（而不是改完补一个恒绿的测试）？
- [ ] 验证报告是否分清了真机实测 / 自动化覆盖 / 未验证？有没有拿退出码 0 当结论？
- [ ] 定时器、订阅、子进程是否都有清理路径（卸载、后台、取消、旧任务晚到）？
- [ ] 用户可见改动是否同改动内更新了 [ui-ux-spec.zh-CN.md](../ui-ux-spec.zh-CN.md)？
- [ ] 有没有把敏感数据写进日志、示例、测试夹具或提交记录？
- [ ] 有没有夹带无关重构、格式化、lint 配置这类把 diff 搅浑的东西？

**PR 描述**面向没参与对话的评审者：问题是什么、改了什么、怎么验证、还有哪些限制。别写"按需求实现 X"这种只有作者懂的省略。

## 合入之后

- 用户可见改动要有人**在真机/真包里点一遍**才算交付完成；点击级验证做不了就要在结论里明说（参考 [../04-测试与验收分层.md](../04-测试与验收分层.md)）。
- 发版改动要检查版本号五处一致，并追加 `src/version/changelog.ts` 条目。
