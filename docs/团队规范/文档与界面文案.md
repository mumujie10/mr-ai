# 文档与界面文案

## 文档口径

- **只留中文。** 新增面向用户或开发者的说明，只写中文一份，**不顺手补英文副本**——双语两份在本项目里是维护负担和漂移源，历史上已经出现过英文版修对了、中文版还在画不存在的目录。
- **新建文档用中文文件名 + 中文标题 + 中文正文**（`docs/` 与 `docs/团队规范/` 已按这个约定）。只有目录索引保留 `README.md` 这个 ASCII 名，因为托管平台目录页会自动渲染它。
- **`cli/` 是例外**：那是内置的第三方派生运行时，自带英文 `README.md` / `CONTRIBUTING.md` / `docs/` 与许可、署名文件。不要按本仓口径去改写或翻译它们——里面的署名与许可件有分发义务，动它们需要单独决定。
- `docs/plans/` 与 `docs/design/` 是**历史档案**：记录当时为什么这样做，不是当前事实的来源。文档与代码冲突时以代码为准，并在同一个改动里把说错的地方改掉（顺手修断链和失效声明，但不要把修补扩大成重写）。
- **教程和引导做进界面里**，不是写成 md。帮助类内容优先考虑界面内的入口与说明，用户不需要去翻文档才知道怎么用。

## 谁改谁更新（硬规则）

改了下面任何东西，**同一个提交内**更新对应用户可见规范：

| 改了什么 | 必须更新 |
|---|---|
| 用户可见的交互反馈、基础组件视觉、动效时长 | [ui-ux-spec.zh-CN.md](../ui-ux-spec.zh-CN.md)（权威口径） |
| 新增刷新 / 重载入口 | 上面文档的"刷新入口清单"章节 |
| 插件 SDK、扩展点、权限目录 | `pnpm plugin-skill:docs` 重新生成 skill 文档（有测试断言，过期即红） |
| 版本发布 | `src/version/changelog.ts` 的 `CHANGELOG_DATA` |

`ui-ux-spec.zh-CN.md` 里每条规则都要求写清**文件和常量名**，并指向回归测试文件名。加规则时按这个格式，"能落到代码"是门槛。

## 变更记录的两个地方

别混淆：

1. **`docs/ui-ux-spec.zh-CN.md` 顶部的变更记录表** —— 界面与交互规范的演进历史（本项目内部使用，随规范改动追加行）。
2. **`src/version/changelog.ts` 的 `CHANGELOG_DATA`** —— **应用内"版本更新"弹窗的唯一数据源**。双语条目、最新在前、需要**人工追加**；只生成外部 Markdown 版本记录文件**不算完成**。同时产出独立版本记录文件时，两处内容要一致。

## 界面文案

- 所有用户可见文本走 `src/i18n`（`zh.ts` / `en.ts`）。**两个语言必须成对**：`builtin-search.test.tsx` 会断言每个 key 在 zh 与 en 下都能解析，缺一边就红。
- key 用 camelCase，按命名空间分组（如 `settings.*`、`chat.*`）。
- 中文是主口径，英文要译到**语义**而不是逐字对应；术语与界面既有说法保持一致。
- 不依赖颜色单独表达状态（要有可访问文本）；错误提示要能说清缺什么、下一步做什么，不用"操作失败"糊过去。
- 反馈不能改变布局（图标状态切换时外层尺寸固定；失败信息用 tooltip 等不推挤布局的方式承载，参考 ui-ux-spec 相应条目）。

## 品牌口径

用户与模型可见的文案统一 **MireAI**。但下面这些**刻意保留原名**，不要顺手改名：

| 保留 | 为什么 |
|---|---|
| `ccgui-next.*` 存储键（localStorage / settings） | 改名会让已有用户的本地状态丢失 |
| `CCGUI_INTERNAL_*` 帧标记与 `[CCGUI internal …]` 后缀 | 已经写进用户历史转录与 `accepted_internal_frames`，改名会让旧会话回放错乱 |
| `CCGUI_*` 环境变量、错误前缀 `CCGUI_PROVIDER_MIGRATION_CONFLICT:` | 跨 Rust/TS 边界的契约，两边同时改才成立 |
| bundle identifier、更新源、签名身份 | 属发布与供应链决策，由维护者定（见 [../01-项目地图.md](../01-项目地图.md) 与发布相关条目） |

## 不写进文档的东西

- 端口、绝对路径、真实账号 / 租户 ID —— 不焊进文档、示例与测试（详见 [安全与隐私红线](./安全与隐私红线.md)）。
- 阶段性结论写成"全部完成"。交付说明以结果为先：改了什么、为什么、如何验证、**还有哪些限制**。
